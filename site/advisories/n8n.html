Security advisory

n8n: a Code node can read another execution's binary data by a caller-built id

This is a source-code review finding in n8n 2.40.6, not an executed exploit. Nothing from n8n was built or run. Every statement below is marked observed, with a file and line citation at commit 024ee46bdc6d57e5c47ef2c26bcac2b3a9efd827, or inference.

The facts come only from the finding pack's source review at that commit. This page carries the full read-path detail, since it is the agreed place for it. It is reachable only by its own URL and is linked from no other page.

Title

Title

A JavaScript Code node task reads another workflow execution's binary data, and in some execution-data modes its whole bundle, by passing a caller-built binary-data id that no layer ties to the running workflow or execution (n8n 2.40.6, source review).

Affected versions

Affected versions

  • n8n 2.40.6, reviewed at commit 024ee46bdc6d57e5c47ef2c26bcac2b3a9efd827. Nothing was run.
  • Observed by reading, at n8n 2.47.2, the three reviewed files on this path. binary-data.service.ts lines 133 to 159 match 2.40.6, including 141 to 143, with only deleteMany changed; blob.manager.ts's getAsBuffer body moved to lines 67 to 71 with only deletion handling changed; binary-helper-functions.ts lines 1 to 237 read the same, including 128 to 153 and 137 to 138.
  • Inference: the read behaviour in those three files is unchanged at 2.47.2. The runner, broker, requester and managers were not available at 2.47.2, so this advisory does not state their 2.47.2 behaviour.

Description

Description

Vulnerable code locations

  • The getBinaryDataBuffer helper exposed to Code tasks (packages/core/src/execution-engine/node-execution-context/execute-context.ts:101-108; packages/@n8n/task-runner/src/runner-types.ts:107-128).
  • The binary-data service's id split and manager dispatch (packages/core/src/binary-data/binary-data.service.ts:139-147, 283-289).
  • The blob manager's read with no parsing (packages/core/src/binary-data/blob.manager.ts:63-66) and the database manager's lookup by fileId alone (packages/cli/src/binary-data/database.manager.ts:66-73).

Read path, observed in source

  • getBinaryDataBuffer is one of seven helper RPC methods exposed to Code user code (packages/@n8n/task-runner/src/runner-types.ts:107-128), bound to makeRpcCall (packages/@n8n/task-runner/src/js-task-runner/js-task-runner.ts:589-607, 653) and sent unchanged in a runner:rpc message (packages/@n8n/task-runner/src/task-runner.ts:510-536).
  • The broker checks only that the task exists, then forwards the message (packages/cli/src/task-runners/task-broker/task-broker.service.ts:336-353).
  • The requester checks that the job exists and the method is on its allow-list, converts serialized Buffers, then calls the method on the task's executeFunctions (packages/cli/src/task-runners/task-managers/task-requester.ts:402-418, 444-452), which is the Code node's own execution context (packages/core/src/execution-engine/node-execution-context/base-execute-context.ts:429-433).
  • getBinaryDataBuffer(itemIndex, propertyName) passes the argument through (packages/core/src/execution-engine/node-execution-context/execute-context.ts:101-108). Any object with mimeType plus data or id passes isBinaryValue (packages/workflow/src/type-guards.ts:103-110) and is used as given (packages/core/src/execution-engine/node-execution-context/utils/binary-helper-functions.ts:137-138).
  • The service splits the id on a colon and picks the manager by that prefix (packages/core/src/binary-data/binary-data.service.ts:139-147, 283-289); the blob manager calls byteStore.read(fileId) with no parsing (packages/core/src/binary-data/blob.manager.ts:63-66), and the EXECUTION_PATH_MATCHER and parseFileId checks are used only for deletion (blob.manager.ts:14, 93-110, 168-183).
  • The database manager looks a row up by fileId alone, with no sourceId filter (packages/cli/src/binary-data/database.manager.ts:66-73). No layer on this path checks that the id belongs to the current workflow or execution, and none rejects .. segments.
  • An ownership check exists elsewhere but not on this path. The editor's GET /binary-data rejects .. segments, its comment noting that the reader resolves the whole path so traversal could read another execution's file (packages/cli/src/controllers/binary-data.controller.ts:58-87), and it checks workflow:read access (binary-data.controller.ts:30-33; packages/cli/src/binary-data/binary-data-access.service.ts:28-73). Neither is reached from the Code-node path.
  • The filesystem manager is always created, the database manager always registered, and the s3 and azure managers registered whenever their store is configured, so the id prefix can select any registered manager (packages/core/src/binary-data/binary-data.service.ts:41-47; packages/cli/src/commands/base-command.ts:359-360, 426-448).

Read path, inference

  • Inference: the filesystem, s3 and azure binary keys are workflows/<wf>/executions/<ex>/binary_data/<uuid v4> (packages/core/src/binary-data/blob.manager.ts:151-160) and database ids are bare uuid v4 values (packages/cli/src/binary-data/database.manager.ts:36), so reaching another execution's binary needs its full id, which would have to leak; guessing the uuid is not practical.
  • Inference: because no layer on the Code-node path ties the id to the running workflow or execution, a task that already knows another execution's id can read that execution's binary file. No run observed this.
  • Inference, from reading @n8n/blob-storage: with the default paths the binary filesystem root is the general storage root (packages/core/src/binary-data/binary-data.config.ts:59; packages/core/src/storage.config.ts:41-46). That root also holds execution bundles at workflows/<wf>/executions/<ex>/execution_data/bundle.json, a key with no random part (packages/cli/src/executions/execution-data/execution-data-json-store.ts:16-28; .../execution-data/constants.ts:5).
  • Inference: those bundles exist only when N8N_EXECUTION_DATA_STORAGE_MODE is filesystem, s3 or azure (the default is database, packages/core/src/storage.config.ts:19-20). In those modes a task that knows another execution's workflow and execution ids could read that execution's whole bundle.json, since execution data's store shares the binary managers' root, bucket or container (packages/cli/src/commands/base-command.ts:426-458, 461-489). No run observed this.
  • Inference: FsByteStore.read confines a key to its root and resolves .. as text, with no realpath step, so symlinks are outside the check (packages/@n8n/blob-storage/src/fs-byte-store.ts:46-54, 101-113); S3ByteStore and AzureByteStore have no path check and use the key as the object key or blob name (s3-byte-store.ee.ts:21-28; azure-byte-store.ee.ts:24-31).
  • Inference: a Code task's output binary object is passed through unchanged (packages/@n8n/task-runner/src/js-task-runner/js-task-runner.ts:445-454; packages/@n8n/task-runner-python/src/task_executor.py:389-390). The Code node result check only requires binary to be an object (packages/nodes-base/nodes/Code/result-validation.ts:48-58), so a later node reading that property by name would read whatever id the Code node supplied (.../utils/binary-helper-functions.ts:139-140).

Steps a reviewer would take

  1. Read the JS Code-node RPC path from getBinaryDataBuffer through the broker and requester to the binary-data service and the blob or database manager, and confirm no layer ties the id to the running workflow or execution.
  2. Confirm that the editor's GET /binary-data download ties the id to workflow:read access and rejects .., and that neither check is reached from the Code-node path.
  3. Check the configured N8N_EXECUTION_DATA_STORAGE_MODE; in filesystem, s3 or azure mode, note that execution bundles share the binary store's root, bucket or container under a key with no random part.
  4. Note, without running an exploit, that reaching another execution's data needs that execution's id, and that where such an id could leak was not established in the pack.

Proof of concept

None run. This is a source review; nothing from n8n was built or executed, and no read of another execution's data was observed. The impact below is inference from the source.

Impact

Inference: a user who can create or edit a JavaScript Code node, and who knows another execution's id, could read that execution's stored binary data, and in filesystem, s3 or azure execution-data mode its whole bundle.json, which holds that execution's data and workflow snapshot. Confidentiality only; no write or denial of service is claimed. No run observed this.

CVSS 4.0, provisional

CVSS 4.0, provisional

PROVISIONAL CVSS 4.0 vector: CVSS:4.0/AV:N/AC:L/AT:P/PR:L/UI:N/VC:H/VI:N/VA:N/SC:N/SI:N/SA:N. It is provisional: it is not computed to a numeric score, and it rests on source review with no run.

Derivation: a network-reachable editor (AV:N); an authenticated user who can edit a Code node (PR:L); knowledge of another execution's id, a precondition outside the attacker's control (AT:P); confidentiality of the vulnerable system only (VC:H), with no integrity or availability impact and no subsequent-system impact. It is provisional because no run measured it.

Mitigations

Mitigations

  • Keep N8N_EXECUTION_DATA_STORAGE_MODE at its database default, so execution bundles are not written to the shared filesystem, s3 or azure store that the binary managers read. Reads follow each execution's recorded storage, so switching back leaves bundles already written in place.
  • Exclude the Code node with NODES_EXCLUDE, as n8n's security audit advises for risky node types. Inference: AI Transform and Code Tool tasks may get the same RPC helpers, so excluding the Code node alone may not close the path, and no setting limiting who can edit Code nodes was read.
