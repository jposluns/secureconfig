# Contributing

Suggestions and guides are welcome. Open a GitHub issue describing the tool or control, or send a pull request; reaching Jeff any other way also works. To request a guide for a specific application that has no guide yet, add a file to the [requests/](requests/README.md) directory per its template, one application per pull request.

## Scope

This repository covers deployment exposure: TLS, authentication, MFA, secret handling, and network exposure for services that AI-assisted projects commonly run. General application security (injection, deserialization, business logic) is out of scope; the guides point to OWASP resources for that, and the [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/) covers LLM-specific application risks such as prompt injection.

## What a guide needs

1. **Verified syntax.** Every configuration line, flag, or variable name must come from the vendor's documentation, with that page linked in a "Sources (checked <month year>)" section. Version-dependent syntax carries a version note; anything time-sensitive (pricing, tiers, defaults that shift) is flagged with "at the time of writing" and a pointer to the source. For whether a control exists at all, the authority is the vendor's reference or CLI documentation, not a quickstart or a quick tour: absence from an introductory page is not evidence that the tool lacks the control. Text Embeddings Inference was first recorded here as having no documented inbound authentication, read off its quick tour, while its CLI reference documents `--api-key`, an `API_KEY` environment variable, and a second listener on `--prometheus-port`.
2. **The standard structure.** Short risk statement, numbered setup steps (bind privately, TLS, authentication, MFA where viable), a Verify section with runnable checks, and Sources. Catalogue guides that cover several tools in one file (for example `admin-uis.md`, `model-servers.md`, `devops-uis.md`) use one section per tool instead of numbered steps, and `common-mistakes.md` is a checklist that links to the fixes rather than carrying its own Verify and Sources. Match the tone of the existing guides: direct, generic placeholders (`example.com`, `203.0.113.10`), no screenshots. Subdomains of `example.com` (such as `app.example.com` or `db.example.com`) and hostnames under `.internal` are fine as placeholders, as are loopback and RFC 1918 addresses when the configuration needs them. `example.net` and `example.org` are reserved by RFC 2606 alongside `example.com` and are equally acceptable. Prose uses Oxford English with `-ize` spellings where both forms are valid, so `authorize` and `randomized` rather than `authorise` and `randomised`, while `analyse` and `paralyse` keep their `-se` because Oxford does. Quoted vendor text is never respelled.
3. **Honesty over coverage.** Where a tool has no native control (no auth, no TLS, no MFA), the guide says so plainly and gives the fronting-layer pattern instead of inventing options.
4. **Working links.** A weekly workflow checks every link; run your additions through it mentally: cite canonical documentation pages, not blog posts. A vendor's own announcement or lifecycle notice (for example a Let's Encrypt or Kubernetes project post) counts as canonical documentation when it is the authoritative statement of a change.
5. **Verify steps must discriminate, and every line must be traced.** Before a guide ships, each configuration line is checked against the vendor page it cites, opened while authoring rather than recalled from memory, and each Verify step is run against the *exposed* state as well as the fixed one. Where standing the exposed state up is impractical, because the project is deprecated or its exposure needs infrastructure the author does not have, the step may instead be reasoned from the vendor's documented behaviour, and the guide marks it at that step as reasoned rather than demonstrated. An unmarked step claims a demonstration, so omitting the mark on a reasoned check is itself a breach of this rule. The allowance is narrow, and marking a step "reasoned" is not a way to skip work: the step must still name the specific prerequisite that was unavailable, give the concrete request or command, state the expected exposed and fixed outcomes, and cite the vendor passage that distinguishes them. Every locally feasible part is still run, because missing infrastructure never waives the shell, placeholder, argument and configuration-parsing checks. Standing a service up is not impractical merely because it runs in a container, nor because a runtime, binaries, or access are currently absent where an available, authorized environment could obtain them and reproduce the exposed state; in that case the stand-up is required. Where no available, authorized environment can reproduce the exposed state, that counts as infrastructure the author does not have, and the step may be reasoned on the same terms as any other unavailable prerequisite. A reasoned step records that nobody has yet observed the behaviour; it never converts an unknown into a verified result. Name the missing capability at the step, in the words that make it checkable ("no container runtime in the authoring environment"), and open a backlog row to demonstrate the step once that capability exists. Reasoned is a debt, not a destination. A guide whose every Verify step is reasoned has not been demonstrated at all, and it may ship only when each step qualifies under the impracticality allowance above and is marked and tracked as that allowance requires; the guide is recorded as not yet demonstrated and is never presented as verified. A check that passes while the service is still reachable is worse than no check at all, because it certifies the exposure. A review brief for a demonstrated step states the exposed run, the fixed run and what each observed, so the reviewer checks the pair rather than infers it. Adding a Verify run means rereading the guide's run-provenance sentence (the one saying what was run, and on what), which otherwise goes stale. `tools/check_guide_shape.py` enforces the structural half of this rule (that a Verify section exists, and that Sources is dated and cites something) and it cannot enforce the rest; tracing each line and proving each check discriminates stay with the author and the reviewer. `README.md` is held to the same contract, with its citations kept in `README.sources.md` so the front page stays readable.
6. **Angle-bracket placeholders in a shell block, which no gate reliably catches.** `<public-ip>`, `<service-user>` and `<user@host>` read as placeholders and run as redirections: `curl -s http://<public-ip>:11434/api/tags` is a read from a file called `public-ip` and a write to one called `:11434/api/tags`, and it fails in whatever way the surrounding command fails, quietly only because `-s` is quiet. Use a house placeholder instead: a reserved address such as `203.0.113.10`, or `REPLACE_WITH_A_NAME` for a value the reader supplies. Which of the two depends on what failing to substitute looks like. A reserved address is usually right in a configuration value or an illustration, though not always: an unreplaced SAN generates a valid certificate for the wrong address, so judge each case on whether leaving the placeholder produces a result the reader would read as success. It is wrong in a Verify probe whose pass is "nothing answered": an unreplaced `203.0.113.10` times out exactly like a blocked port, so the check passes for the wrong reason. Those take `REPLACE_WITH_A_NAME`, and the check must REJECT the unsubstituted value locally rather than rely on it failing to resolve. Resolution is not a guarantee: a wildcard resolver answers anything, an `http_proxy` in the environment makes the target's name irrelevant, and a local socket error produces the same exit code as a remote refusal. Guard it in the block, and put the command INSIDE the guard so it cannot run unsubstituted; a guard that only prints a warning and then runs the command anyway leaves the original false pass intact. Carry the value in the shell's positional parameters inside a subshell rather than in a named variable, and handle the empty case for a reader who pastes only part of the block. A named variable belongs to the reader's environment as much as to the block: five successive guard designs were beaten in turn by a prefix-only pattern, a partial paste, `set -u`, a placeholder embedded in a longer value, and finally a `readonly` variable already set in the reader's shell, which makes the block's own assignment fail while the probe runs on the inherited value. Positional parameters close the attribute and inheritance bypasses together, because they cannot be made `readonly`, cannot carry `declare -i` or `declare -l`, and are never inherited from the environment. They do not close the partial paste, and on that one case they are worse than the variable they replaced: an omitted assignment left a variable unset and the guard caught it, whereas an omitted `set --` line leaves the caller's own arguments in place and the guard reads those instead. The partial paste is narrowed by two checks together, and it is worth being exact about what they do and do not reach. The block's `set --` line opens with a fixed marker, and the guard lines below it check that marker and then count the values. A fragment that keeps those guard lines but omits or shortens the `set --` line is caught by them; a fragment pasted from below the guard lines is unguarded, as any paste that starts past a guard would be, so the protection is in pasting whole blocks, not in the guard reaching code that precedes it. Measured: a marker alone lets a short assignment crash on an unset positional under `set -u` instead of printing the guard message, and a count alone is passed by any shell holding the expected number of plausible values. Quote the count as `"$#"`. Unquoted it is a bypass and not a nuisance: a reader whose `IFS` contains a digit that ends the count has that expansion split apart, so under `IFS=0` a block requiring one value accepts ten, the test reads `1 -eq 1`, and the command runs. Give every probe `-g` as well, because curl expands `[...]` and `{...}` in a URL whatever the shell did with the quotes. Neither reaches the last case: a shell that already holds the marker AND the right number of values is indistinguishable, from inside the block, from the block having set them. That case is irreducible in a pasted fragment, and this is the fifth successive design in this lineage, so the rule to draw is the one about claims rather than about shells. State per-case what a guard was measured to catch, never an aggregate that it closes a class. Two assumptions remain, and a guide should not pretend otherwise: the block needs a shell whose builtins are the real ones, since a reader who has shadowed `set` or `[` with a function or alias defeats every guard at once, and a value containing a literal apostrophe cannot simply be dropped inside the quotes. Single-quote the placeholder on the `set --` line, and say in the guide that the reader substitutes inside the quotes. A guard cannot help with what happens before it runs: an unquoted substitution site is evaluated by the shell as it parses the line, so a pasted URL containing `&` backgrounds the `set --` itself and leaves the parameters empty while the remainder of the line runs as its own command, and one containing `$(...)` or a backtick simply executes. That is a sixth way past a guard that the first five fixes do not touch, because it lands before the guard exists:

   ```bash
   (                                       # a subshell, so your own script arguments are untouched
     set -- PASTE_WHOLE_BLOCK 'REPLACE_WITH_YOUR_PUBLIC_IP'
     [ "${1-}" = PASTE_WHOLE_BLOCK ] || { echo "paste the whole block, including its set -- line; not probing"; exit; }
     shift
     [ "$#" -eq 1 ] || { echo "the set -- line needs exactly 1 value; not probing"; exit; }
     case "$1" in
       *REPLACE_WITH_*|*YOUR_PUBLIC_IP*|"") echo "substitute your own address on the set -- line above; not probing" ;;
       *) curl -q -g -s -o /dev/null --noproxy '*' --connect-timeout 5 --max-time 20 \
            -w 'http=%{http_code} exit=%{exitcode} err=%{errormsg}\n' "http://$1:3000/" ;;
     esac
   )
   ```

   The subshell also contains `exit`, so a guard may end the block early at the cost of a subshell rather than the reader's interactive session; the same `exit` pasted at top level would close that session, so keep the parentheses when adapting the shape. Add `--noproxy '*'` to any probe described as direct, since an `http_proxy` in the environment otherwise produces the documented pass without the address mattering, and report `err=%{errormsg}` alongside `exit=%{exitcode}` (both added in curl 7.75.0) so the reader judges the error text rather than a bare number, which certifies nothing about the remote state. Some shapes do trip an existing check, by accident rather than design: shellcheck reports SC2217 or SC2261 for a few of them, and `check_prose_conventions.py` catches a bracketed host outside the house placeholder set. That is not coverage, and three shapes are recorded as passing in `tools/test_shell_blocks.py`. Treat it as a review obligation: five successive rules were written to catch it and all five were beaten by legal shell a guide could plausibly carry, the last by an ordinary `sed` substitution, so the gate that tried was removed rather than left producing false alarms. The docstring of `tools/check_shell_blocks.py` records what each attempt lost to.

7. **Credentials go on stdin, never in curl's argv.** A password, token, API key, service-token secret, or a presigned URL passed on the command line (`-u user:PASSWORD`, `-H "Authorization: Bearer TOKEN"`, a signed `"$URL"` operand) is readable through `ps` and `/proc/<pid>/cmdline` to local observers while it is there, including before curl scrubs supported arguments on some platforms, and single-quoting does not change that: quoting stops the shell interpreting the value, but the value still lands in argv once expanded. Feed the secret to curl on stdin. For a header, pipe the built line to `--header @-` (`printf 'Authorization: Bearer %s\n' "$1" | curl ... --header @-`); for basic auth, a request body, or a signed URL, pipe a curl config file to `--config -` (`printf 'user = "admin:%s"\n' "$1" | curl ... --config -`, and `data-binary = "..."` or `url = "..."` for the other two). Because a config value is double-quoted, escape a backslash and then a double quote in the substituted value (`set -- "${1//\\/\\\\}"` then `set -- "${1//\"/\\\"}"`) and reject a control character in the guard, so a pasted newline cannot inject a second directive or header. Keep the secret in the subshell's positional parameters and the builtin `printf`, never export it, and do not copy it into a named variable (rule 6), with one exception. `read` cannot write to the positional parameters, so a secret prompted with `read -r -s` may land in a single variable local to the block's subshell. Three conditions apply. First, tracing and allexport are off (`set +x +a`) before the read; under an inherited `set -a`, `read` would give the variable the export attribute. Second, the variable is cleared first with `unset -n` and then `unset -v`, and the block fails closed if either fails, because a readonly or nameref'd name can come from the reader's shell and a plain `unset -v` on a nameref clears its target instead. Third, the variable is never exported. `search-engines.md`'s paired block is the model. A secret the reader already holds in an environment variable is not covered by this exception; prompt for it instead. This closes the argv channel only: it does not hide the secret from shell history, `set -x` tracing, or the account owner's own view of the process, so say as much and do not sell it as complete secret protection. A second exception, to the stdin rule rather than to the named-variable one, covers a tool that accepts a secret outside argv only through its environment, as natscli reads `NATS_PASSWORD`, `nomad` reads `NOMAD_TOKEN` and `surreal start` reads `SURREAL_PASS`. It applies only where the tool, at the version the guide covers, offers no stdin or file input for that secret; where such an input exists it is preferred, and the vendor's reference decides whether it does (rule 1). Pass the secret as a one-command prefix assignment (`NATS_PASSWORD="$1" nats ...`), taking the value from the positional parameters or the `read` exception's variable, and never `export` it. This moves the secret out of argv, not out of reach: while the command runs, its environment is readable by the same user (and by root) through `/proc/<pid>/environ`, and unless the tool clears it, every process the tool starts inherits it, so say as much in the guide. A deliberate NON-secret in a probe (a dummy bad key, or a known-wrong password whose whole point is to be refused) is not a credential: leave it in argv and mark the line `# guard-conventions: allow <reason>` so the gate does not flag it. `tools/check_guard_conventions.py` enforces this as checks C3-USER-ARGV, C3-HEADER-ARGV, C3-BODY-ARGV and C3-URL-ARGV over every fenced shell block; it recognizes the `@-` and `--config -` stdin forms. It is a bounded lexical scan with disclosed blind spots, not a full curl parser: a credential in a shell variable or command substitution, a curl reached through a variable, alias, or `eval`, and an opaque `--cookie`/`--netrc` secret are known false negatives that rule 5's tracing obligation still covers.

## Shipping a change

`VERSION` names the most recently merged pull request, as `1.0.<number>`. That number is knowable
only once the pull request exists, so the authoring step is: open the pull request, write its number
into `VERSION`, push, then merge. A pull request that sets its predecessor's number is stale the
moment it lands, which is what #46 did and #47 corrected.

Merge in numeric order. Where that is not possible, the higher-numbered pull request sets the value,
whichever of the two merges last, because the rule read literally makes the number go backwards when
an older one merges last: #50 merged after #51 and set `1.0.50` against a `main` already at
`1.0.51`. So a pull request that merges after a higher-numbered one leaves `VERSION` alone. No gate
enforces this; the suite is offline by policy and a pull request number is only knowable from
outside.

Record the change in `CHANGELOG.md` in the same pull request, not in a later bookkeeping one. A
required gate checks that every merged pull request is referenced, exempting only the newest, so a
second unrecorded merge turns the build red. Eight pull requests had gone unrecorded before that
gate existed.
