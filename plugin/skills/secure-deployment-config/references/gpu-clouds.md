Unlike the major clouds, most rented-GPU platforms put no default-deny firewall in front of the box. How a bound port becomes public differs by platform: on RunPod you expose a port (HTTP or TCP), on Vast.ai a launch mode or an added port maps it to a public port, on Lambda you open a firewall rule (its inbound firewall is deny-by-default), and on Modal it depends on the serverless construct. Raw port publication and a firewall allowance add NO authentication of their own, so a listener exposed that way is reachable with only whatever auth it has itself; an authenticating platform proxy is the exception (Modal's Endpoints and Servers require proxy auth by default and Shared Endpoints always do, only a public Web endpoint does not, and Vast.ai's Instance Portal gates the routes it proxies), but do not assume one is in front of a given port. Treat every listener the same way you would on your own hardware: bind it privately or authenticate it, per [ollama.md](ollama.md) and [model-servers.md](model-servers.md).

## RunPod

Exposed HTTP ports (the "Expose HTTP Ports" pod setting) go through RunPod's proxy at `https://[POD_ID]-[INTERNAL_PORT].proxy.runpod.net`; the proxy terminates HTTPS automatically, "All connections are secured with HTTPS, even if your internal service uses HTTP," but the resulting URL is publicly reachable by anyone who has it, so a bare Jupyter server or model API on an exposed HTTP port still needs its own authentication.

Exposed TCP ports get "direct TCP forwarding with a public IP address" instead, and TLS is not automatic there: RunPod's own docs say to "implement TLS in your application when handling sensitive data over TCP." Secure every template listener, including notebooks, before exposing its port; a notebook exposed as raw TCP with no application-level password is fully open.

A "symmetrical port mapping" option lets a template ask for matching internal and external port numbers by specifying a value above 70000 in its TCP configuration. That value is not a port: RunPod's documentation says such numbers are not valid ports and serve only to signal the request, and the real assignment arrives in the pod's environment (for example `$RUNPOD_TCP_PORT_70000`). It is a convenience for the pod's own scripts, not a security boundary, and the port is still public once mapped.

## Vast.ai

Rented instances open ports per launch mode (port 22 for SSH mode, port 22 plus 8080 for Jupyter mode by default); each internal port maps to a random external port on a shared public IP, and once a port is mapped it is reachable from the internet with no firewall step described in Vast.ai's docs.

The Instance Portal fronts web apps on the instance with a reverse proxy (Caddy) when the external and internal ports differ, and secures access with a token rather than a login: "a secure token is appended to the link to prevent unauthorised access to your applications." At base-image commit 00064421641881c1f83ff58c55f13cbc10cbea4d, the README documents OPEN_BUTTON_TOKEN for Basic/Bearer access, WEB_PASSWORD as a custom password, ENABLE_AUTH=false to disable authentication (default true), and AUTH_EXCLUDE as external ports excluded from authentication. PORTAL_CONFIG defines portal entries and port routing; equal external/internal ports bypass proxying. The auth test code uses both tokens as Bearer credentials and WEB_PASSWORD for Basic auth; these are test expectations, not observed results. The Caddy launcher delegates configuration to portal-aio; the delegated configurator is now cited at the same commit, and the next two paragraphs trace variable precedence and route enforcement from it. In this guide's assessment, routing configuration is not a credential. A token-bearing link IS the credential: anyone who has that URL is authenticated, so treat it as a secret and share it only with intended recipients (stripping the token is useful for testing that anonymous access is refused). Do not assume an app is private just because it sits behind the portal's port remapping, and confirm the route is one the portal actually authenticates.

What the cited configurator shows, at the same commit: it reads `PORTAL_CONFIG` only when `/etc/portal.yaml` does not exist, writes the parsed entries back to that file (so the file, once written, takes precedence over the variable), and emits a Caddy listener only for an entry whose external and internal ports differ and whose external port has a `VAST_TCP_PORT` mapping in the environment; an entry with equal ports, or with an unmapped external port, gets no Caddy listener, so nothing in the generated configuration authenticates it. A boot script rewrites `PORTAL_CONFIG` for Jupyter: it drops Jupyter entries when `VAST_TCP_PORT_8080` is absent or empty, or when `/.launch` exists without a Jupyter match and `JUPYTER_OVERRIDE` is not `true` (case-insensitively). Re-addition requires no `/.launch`, a nonempty mapping, no existing Jupyter entry and `FORCE_JUPYTER` not equal to `false` (case-insensitively). When `/.launch` contains Jupyter and `JUPYTER_OVERRIDE` is not `true` (case-insensitively), it rewrites `localhost:8080:18080` to `localhost:8080:8080`; these equal-port entries get no generated Caddy listener or portal authentication only if the rewritten environment is used, since an existing `/etc/portal.yaml` takes precedence. Authentication stays on unless `ENABLE_AUTH` equals `false` case-insensitively; any other value, including unset, keeps it on. `WEB_PASSWORD` and `OPEN_BUTTON_TOKEN` have no precedence over each other: when neither is set, one generated value is used for both; when only one is set, the other mirrors it; when both are set, every matcher accepts either, so each is a full credential on every port the portal protects. A protected port accepts a `token` query parameter, an auth cookie named after the container label, or an `Authorization: Bearer` header, each matching either token, and falls back to HTTP Basic with `WEB_USERNAME` (default `vastai`) and a hash of `WEB_PASSWORD`; a valid query token sets the auth cookie. The generated listeners serve plain HTTP unless `ENABLE_HTTPS` is `true` and a valid instance certificate and key are present.

The exemptions are the part to check. `AUTH_EXCLUDE` is a comma-separated list matched on the EXTERNAL port, and an excluded port is proxied with no authentication at all, as is every port when `ENABLE_AUTH=false`: both are exposures. Even on an authenticated port, a fixed set of paths bypasses every credential check: `/portal-resolver` is answered directly with 200, and `/.well-known/acme-challenge/*`, `/.well-known/change-password`, `/manifest.json`, `/manifest.webmanifest`, `/site.webmanifest`, `/.well-known/security.txt` and `/security.txt` are reverse-proxied to the backend with no credential, so an app that serves private content on one of those paths is anonymously reachable through the portal. The configurator prints the effective username and credentials to its console output, and `OPEN_BUTTON_TOKEN` is reused beyond the web routes: the portal launcher and the Syncthing supervisor script use it as the Syncthing GUI API key (the supervisor script falls back to a random value only when the variable is unset or empty), and the desktop template's VNC password fallback under Common mistakes reuses it as well, so, in this guide's reasoning, a token-bearing link shares those reused credentials too. The portal's capabilities manifest reports the same variables but is not the enforcement point: both reporting and enforcement lowercase `ENABLE_AUTH` and default an unset value to `"true"`; reporting tests equality to `"true"`, while enforcement tests inequality to `"false"`, so other values (including empty) are enforced but reported as disabled.

## Lambda

Lambda's Public Cloud firewall is deny-by-default for inbound traffic with two exceptions: "By default, Lambda allows only incoming ICMP traffic or TCP traffic on port 22 (SSH)." Everything else, a Jupyter notebook, a model server port, needs an explicit firewall rule (global, workspace-wide rules, or a per-instance ruleset attached at launch); Lambda's own guidance is blunt about the tradeoff: "Each port you open increases the attack surface of your instances."

Opening a rule makes the port reachable from whatever source range you allow, with no authentication of its own, so pair the rule with the listener's native auth or a proxy in front, not the firewall rule alone.

## Modal

Modal's serverless constructs default differently by shape, and the control differs too. Web endpoints (the current decorator is `modal.fastapi_endpoint`, which replaced `@web_endpoint`) are "publicly available by default" and stay public until the function sets `requires_proxy_auth=True`. A Dedicated Endpoint is made public with the `--unauthenticated` flag; a Server sets `unauthenticated=True` on `@app.server(...)` instead of that flag; and a Shared Endpoint always requires a Proxy Token: Modal's Shared Endpoints page says "Shared Endpoints always require a proxy token," and its Endpoints page's Proxy tokens section says Shared Endpoints always require one while "Dedicated Endpoints can also be created with `--unauthenticated`." The cited pages document the unauthenticated option for Dedicated Endpoints only, so, in this guide's assessment, a Shared Endpoint cannot be made public. Name the construct you are deploying and check its actual control rather than assuming one flag covers all of them.

Where proxy auth is enabled, callers authenticate with a Token ID and Token Secret pair, either as separate `Modal-Key` and `Modal-Secret` headers or combined as `Authorization: Bearer <token_id>.<token_secret>` (Modal notes this mirrors "the same scheme the OpenAI API uses"). A protected endpoint called without credentials returns 401 with "missing credentials for proxy authorization." Check which default your construct uses before deploying; do not assume a Web Function is private.

## The pattern, whatever the platform

The platform's own controls (RunPod's proxy TLS, Vast.ai's portal token, Lambda's firewall rules, Modal's proxy auth) are necessary but not sufficient on their own. How to bind the model server depends on which kind of proxy is in front of it. RunPod's HTTP proxy reaches the pod over its exposed network interface rather than through a local backend, so the service must bind `0.0.0.0` inside the pod; RunPod's own troubleshooting guidance is explicit that binding to `localhost` only will keep the proxy from reaching it. Vast.ai's Instance Portal is the opposite case: it is a local reverse proxy (Caddy) running on the instance itself, so the app it forwards to can stay on loopback behind it, the same pattern as an authenticating proxy on your own hardware. Whichever binding the platform's proxy needs, add the listener's OWN authentication where it supports one; where it does not, keep the unauthenticated backend private and put an authenticating gateway in front, so the gateway and not the bare listener is what the platform exposes, exactly as [ollama.md](ollama.md) and [model-servers.md](model-servers.md) describe. At Ollama v0.34.2, the cited local API route setup installs CORS and host filtering without an inbound credential check. Cloud sign-in and OLLAMA_AUTH client outbound signing are separate from local inbound authentication. A platform-level control that changes later, a firewall rule widened to a broader source range, a template rebuilt without a flag, should not be the only thing standing between the listener and the internet (deleting a Lambda allow rule, by contrast, closes the port rather than opening it).

MFA: this guide cites no platform feature that adds a second factor to the workload itself, so workload authentication must be verified separately. This guide's advice is to enable MFA on each RunPod, Vast.ai, Lambda, and Modal platform account ([mfa.md](mfa.md)); no account-security source for these platforms is cited here. In this guide's reasoning, an API key or proxy-auth token secures a machine client and is a separate control from the platform login.

SSH: authenticate with your own key, not a password. Lambda requires an SSH key at launch; Vast.ai disables password authentication and uses the key you register; RunPod recommends key auth and offers an optional password you should skip. Keep the private key off the instance, and treat SSH access as a control separate from the platform login above.

## Common mistakes

- Assuming a rented box has a default-deny firewall like a major cloud's security group; most rented-GPU platforms do not.
- Treating a template's HTTPS proxy URL as proof the underlying service is authenticated; the proxy secures transport, not access.
- Overlooking a template's remote desktop: at Vast.ai base-image commit 00064421641881c1f83ff58c55f13cbc10cbea4d, the linux-desktop launcher configures x11vnc on port 5900 with a password from VNC_PASSWORD, falling back to OPEN_BUTTON_TOKEN when VNC_PASSWORD is unset or empty. The template README describes OPEN_BUTTON_TOKEN as randomly generated on first boot and visible in instance logs, and offers Selkies WebRTC and Guacamole browser VNC alongside direct VNC. These citations do not establish other templates' ports or password defaults, or the strength of the effective VNC password. This guide's advice: check both browser and direct VNC listeners and their public mappings for missing or weak authentication. In this guide's reasoning, the browser page's HTTPS does not protect a separately reachable VNC connection, so a direct VNC mapping needs its own strong password and an encrypted tunnel, or should be kept off the public mapping. This guide's advice: test a direct VNC mapping with a VNC client, since the browser access controls and the HTTP status checks above may not cover it.
- Leaving a Modal Web Function without `requires_proxy_auth=True` because Endpoints and Servers are private by default and it is easy to assume Web Functions are too.
- Reusing a rented box's platform login (RunPod/Vast.ai/Lambda/Modal account) as if it were the same thing as the workload's own authentication; they are separate controls.
